**Status** Accepted

## Context

- **Both are secrets presented on [authentication](../api/overview.md#authentication)**, so the instinct is to hash both the same way, with the slow algorithm, because slow is safe
- **That instinct is wrong here.** Applied uniformly, it costs real latency for no security gain

## Decision

**Two algorithms, for two different threat profiles.**

### Passwords: Argon2id

```python
PasswordHasher(time_cost=3, memory_cost=65536, parallelism=4,
               hash_len=32, salt_len=16, type=Type.ID)
```

- Passwords are **low-entropy**, human-chosen, reused across sites, and present in dictionaries
- **Slow hashing is the entire defence**
- The cost is paid **once per login**

### API keys: HMAC-SHA256 under a server-side pepper

```python
hmac.new(settings.api_key_pepper.encode(), plaintext.encode(), hashlib.sha256)
```

- An [API key](../security/api-keys.md#format) is 32 characters from a 62-character alphabet, generated by a CSPRNG: **about 190 bits**
- No dictionary, no reuse, no human pattern, **no feasible brute force** to stretch against
- **Argon2 would add 50-100 ms to every authenticated request** and buy nothing: there was no brute-force surface to protect
- **The [pepper](../security/secrets.md#pepper) is server-side only** (`API_KEY_PEPPER`), never in the database, so a dump does not let an attacker verify a guessed key offline
- **Comparison is always `hmac.compare_digest`**

## Alternatives rejected

| Alternative | Why it lost |
| --- | --- |
| **Argon2 for both** | Consistent, and 50-100 ms slower per request for a guarantee that was already free. At [240 requests a minute per principal](../api/overview.md#rate-limiting), a material throughput cost |
| **Plain SHA-256 with no pepper** | Fast and constant-time, but a database dump alone lets an attacker verify guesses offline. The pepper costs nothing and removes that |
| **Store keys encrypted, not hashed** | Reversible, so something somewhere can reveal a key. Hashing means **nothing** can |

## Cost

- **Two code paths, and a rule that has to be understood rather than followed**: exactly what a future contributor "fixes" into consistency
  - **mitigations:** the rule is stated at the top of [`app/core/security.py`](../../backend/app/core/security.py), and [`tests/unit/test_security.py`](../../backend/tests/unit/test_security.py)`::test_keys_are_hmac_hashed_not_argon2` fails if someone unifies them
- **Pepper rotation is expensive**
  - rotating `API_KEY_PEPPER` invalidates every stored hash
  - there is no re-peppering without the plaintext, which is gone by design
  - so a pepper rotation means **rotating every API key** in the system
  - the correct trade for a value that never has to be read back, but it must be planned before it is needed. See [secrets](../security/secrets.md#pepper)
- **Update (2026-10-11): the pepper keys more than API keys**
  - `hash_opaque_token` in [`app/core/security.py`](../../backend/app/core/security.py) applies the same HMAC to refresh-session handles, email-verification and password-reset tokens, and notification-channel secrets
  - so a pepper rotation also stops every refresh session from refreshing (users sign in again when their access token expires), and voids outstanding reset and verification links
  - webhook signatures do **not** change: they are keyed by the channel secret's stored hash, which a rotation leaves in place ([`handlers.py`](../../backend/app/workers/consumers/handlers.py)). The same fact means a receiver holding only the plaintext secret cannot verify them, which is a defect in the signing, not in this decision
